## 摘要
尽管编码代理在处理日益复杂的任务方面取得了进展，但它们仍然倾向于引入意外的编辑、微妙的错误和范围漂移，这些往往能逃过代码审查，这意味着开发者仍必须决定赋予它们多少自主权。然而，现有的设置代理自主级别的方法（如静态权限设置或指令文件）无法解释开发者对代理自主性的偏好如何在不同任务和不同时间发生变化。我们对21名使用编码代理的软件工程师进行了一项形成性调查，发现他们在校准自主性方面感到沮丧，并且对监督水平的偏好是不断演变的。基于这些见解，我们提出了Hedwig，一个CLI编码代理，它能根据跨会话的开发者-代理交互动态调整其自主性级别。与全局固定的自主性配置不同，Hedwig从开发者的决策和反馈中学习一套不断演变的行为准则，减少代理已赢得信任的工作中的摩擦，同时在代理操作超出熟悉范围时加强监督。Hedwig展示了一种新范式的潜力，其中代理通过积极、纵向的协作，根据用户信任智能地调整其自主性水平。

## Abstract
Despite coding agents' advances in handling increasingly complex tasks, their continued tendency to introduce unintended edits, subtle bugs, and scope drift that slip past code review means developers must still decide how much autonomy to grant them. However, existing approaches for setting an agent's level of autonomy, such as static permission settings or instruction files, cannot account for how developers' preferences for agent autonomy can shift across tasks and over time. We conducted a formative survey with 21 software engineers who use coding agents and found that they experience frustration with calibrating autonomy and have evolving preferences for level of oversight. Building on these insights, we present Hedwig, a CLI coding agent that dynamically adjusts its autonomy level based on developer-agent interactions across sessions. Rather than operating on a global, fixed autonomy configuration, Hedwig learns an evolving set of behavioral guidelines from developer decisions and feedback, reducing friction on work for which the agent has earned trust, while tightening oversight when the agent operates outside familiar territory. Hedwig demonstrates the potential of a new paradigm where agents intelligently adapt their level of autonomy based on user trust through active, longitudinal collaboration.

## 1. 论文的核心问题与整体含义（研究动机和背景）

- **核心问题**：当前编码代理（coding agents）虽然能处理复杂任务，但仍频繁引入意外编辑、细微错误和范围漂移，且这些缺陷常能逃过代码审查。开发者需要决定赋予代理多少自主权，但现有的静态权限设置或指令文件（如 AGENTS.md、CLAUDE.md）无法适应开发者偏好随任务和时间的动态变化。
- **研究动机**：对21名经验丰富的编码代理使用者进行形成性调查发现，开发者对校准自主性感到沮丧，其监督偏好是不断演变的。例如，11/21的开发者希望仅在关键里程碑检查，2/21希望仅在发生风险或意外时检查；同时，开发者担心代理引入细微错误（13/21）、侵蚀自身对代码库的理解（12/21）、安全漏洞（10/21）等。
- **整体含义**：人机协作的目标不是最大化自动化，而是根据开发者的风险容忍度、任务风险等级和对代理信任的演变，维持有意义的、可调的人机监督。作者主张代理应具备自适应自主性（dynamic autonomy），通过纵向交互学习并调整行为。

## 2. 论文提出的方法论：核心思想、关键技术细节

- **核心思想**：Hedwig 是一个 CLI 编码代理，它记录开发者与代理的交互痕迹（如代码编辑审批、计划修正、命令拒绝/批准、明确指导），通过两条并行路径动态调整自主级别：
  - **策略路径（Policy Path）**：训练一个在线逻辑回归分类器，基于13维特征向量（包括 diff 大小、影响范围、变更模式风险、先前批准/拒绝计数、安全敏感性、验证失败历史、模型置信度等），决定是否需要进行检查（check-in）。分类器使用随机梯度下降（SGD）从交互历史中持续更新，系数按仓库持久化，实现跨会话个性化。
  - **检索路径（Retrieval Path）**：将开发者修正和明确指令存储为短文本片段，在后续任务中根据相关性检索并注入到模型提示中，从而定性引导模型行为，但不暴露底层策略状态。
- **两种自主性策略**：
  - **硬约束（Hard Constraints）**：在 CLI 层强制执行的严格边界，例如禁止修改受保护路径，独立于模型推理，不可被模型绕过。
  - **行为指导（Behavioral Guidance）**：较软的偏好，例如“何时应谨慎”“何时应询问输入”，通过检索影响模型推理，同时被策略引擎独立监控。
- **检查机制**：每个提议动作通过三层审批级联：先检查硬约束，再经过学习策略引擎评分。评分结果分为：自动静默批准（高于 proceed 阈值）、批准但显示摘要（中间带）、触发实时检查（低于 flag 阈值）。检查的同时提供简洁解释，说明与历史交互的关系。
- **跨检查透明性**：会话结束时，系统分别报告策略触发的检查（policy-initiated）和模型主动触发的检查（agent-initiated），使两层架构对开发者可见。

## 3. 实验设计：数据集、场景、对比方法

- **任务场景**：两个后端任务（T1：添加 GET /tasks/summary 端点；T2：扩展为可选 priority 过滤器），共产生 11 次写操作。运行在小型 Python 任务 API 仓库上，包含路由处理器、服务层、测试文件和任务规范文件。
- **对比方法**：Claude Code（CC）搭配 Auto Memory。
  - CC-C：手动编写 CLAUDE.md 模仿谨慎人格（要求所有 API 更改前必须征得批准）。
  - CC-P：手动编写 CLAUDE.md 模仿宽容人格（允许自主执行常规后端更改）。
  - CC-B：无 CLAUDE.md 作为基线。
- **基准（Oracle）**：使用 Claude Opus 4.7 作为 LLM 裁判，根据预设人格规则和操作上下文，对每个操作是否需要检查进行标注。谨慎人格下 4 个操作需要检查；宽容人格下 0 个。
- **评估指标**：检查次数（Check-in Count / Ratio）、召回率（Recall，必需检查中被系统捕获的比例）、精确率（Precision，系统检查中符合必需要求的比例）。
- **Hedwig 的设置**：为每个开发者人格（谨慎/宽容）预制 20 条合成决策，并回放 3 次（共 60 次有效梯度更新）使分类器达到稳定状态。此外，根据批准率推断自主性偏好：批准率≥90% 触发 prefer_fewer_checkins 和 skip_low_risk_plan_checkpoint。

## 6. 论文的主要结论与发现

- **Hedwig 能够根据开发者历史自适应调整检查频率**：谨慎人格下检查比率为 0.55，宽容人格下为 0.36，差距达 19 个百分点，且完全源自不同的信任数据库和批准率推断的偏好。
- **Hedwig 在捕获必要检查方面优于 CC**：针对谨慎人格的 LLM 法官标注的 4 个必需检查，Hedwig 全部捕获（召回率 1.00），而 CC-C 仅捕获 2 个（召回率 0.50），CC-B 为 0。CC-C 即使写了明确指令，仍跳过了两个签名变更操作。
- **Hedwig 具有安全优先的权衡**：宽容人格下 Hedwig 产生 4 个误报（即不必要的检查），而 CC 为 0。作者认为这在治理场景中是可接受的，因为漏检（未审查的 API 更改发布）的代价远高于多余检查（开发者花费几秒时间）。
- **Hedwig 的架构优势**：它将监督外部化为一个持续更新、可检查的策略，同时利用模型侧推理作为有用但非权威的信息来源，实现了监督的“选择性、可读性和可调节性”。

## 7. 优点：方法或实验设计上的亮点

- **创新方法论**：提出自适应自主性的具体架构，将监督分为硬约束与行为指导两条路径，并利用在线学习从交互历史中自动调整检查策略，超越了静态指令或记忆方法。
- **可解释性与透明度**：会话结束后区分策略触发和模型触发的检查，并提供检查原因说明；开发者可通过命令（如 `hw observe preferences`、`hw observe weights`）直接查看存储的偏好和系数变化，便于信任控制。
- **双向调整能力**：不仅允许信任通过批准积累而扩大，还允许开发者有针对性地撤销特定主题的信任（如 `revoke –topic api`），而不丢弃其他状态，实现了精细的动态监督。
- **实验设计中的 Oracle 基准**：使用独立 LLM 作为裁判对每个操作进行必要检查标注，提供了客观的第三方评价参考，使召回率和精确率的计算有依据。
- **开源实现**：提供完整源代码（GitHub），便于复现和扩展。
