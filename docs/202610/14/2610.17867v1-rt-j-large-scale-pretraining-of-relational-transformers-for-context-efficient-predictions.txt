Abstract 

Foundation models for tables and relational databases are increasingly used for predictive tasks across various scientific and industrial domains. However, adapting existing models to unseen datasets requires tens of thousands of examples. Here we introduce RT-J , an 85 M-parameter relational foundation model (RFM) that makes accurate predictions even with hundreds of in-context examples or fewer. To achieve this, we first assemble THE JOIN , a large collection of 639 web-crawled databases with 6,023 LLM-generated forecasting tasks. We pretrain with long contexts of up to 8,192 database cells, using in-context examples from a novel lightweight random-walk retriever. Finally, we leverage context tuning and ensembling to scale up test-time compute. On in-context regression tasks from RelBench, RT-J requires 10 × fewer examples on average to match strong feature engineering pipelines with LLM-agent or RDBLearn featurizers and TabICLv2 or LightGBM predictors. Overall, our work pushes the frontier for context-efficient predictions on relational data and highlights the importance of real-world semantics, context engineering and large-scale pretraining for RFMs. 

1 Introduction 

Foundation models have transformed how machine learning systems are adapted to new tasks [1, 2]. In language and vision, pretrained models can often solve new tasks using only a small number of examples in context [3, 4]. Yet this capability remains largely out of reach for relational data, even though relational databases and data warehouses store much of the world’s structured enterprise, scientific, and operational data [5, 6]. Today, strong relational predictors typically require task-specific training [7–9], or substantial labeled data [10–16]. This limits predictive modeling precisely in the settings where it is most valuable, including cases where labeled examples are scarce, and users need rapid ad hoc predictions for decision-making. Tabular foundation models (TFMs) like TabPFN [17, 18] and TabICL [19, 20] provide in-context learning for single-table prediction, and systems such as RDBLearn [21] extend them to relational databases by aggregating relational neighborhoods into engineered features. Such an approach can be effective with many labeled examples, but it flattens the database and removes the explicit relational structure needed to effectively reason over entities, relationships, and cross-table dependencies. Natively relational architectures like RelGT [8] and RelGNN [7] operate directly on multi-table databases by representing rows as nodes and primary–foreign-key links as edges, but require training for each schema and task. 2 Background: Relational Transformers for Predictive Tasks on Databases 

Relational databases and relational structure. Let D denote a relational database with schema graph G = ( T , E), where each node T ∈ T is a table and each directed edge ( eT , T ) ∈ E indicates that table T contains a foreign key column referencing the rows of the parent table eT . Each table T

contains rows indexed by primary key(s) and columns consisting of numerical, categorical, textual, or temporal values, and optional foreign keys. Thus, the relational structure of D is characterized by the schema graph along with row-level bipartite connectivity via primary–foreign key links [6, 26, 29]. 

Prediction tasks on relational data. A prediction task specifies a target table T ⋆, a target column 

c⋆, and a set of prediction rows I in T ⋆. For each row r ∈ I , the target value is yr = xr,c ⋆ . The goal of a foundation model fθ is to predict yr from the observed relational context around row r.For boolean or categorical targets, fθ outputs a class distribution. For numerical targets, it outputs a real-valued prediction. This formulation covers both (1) autocompletion and (2) forecasting tasks. In an autocompletion task, T ⋆ is an existing database table and c⋆ is one of its columns (such as imputing the price of a transaction). In a forecasting task, T ⋆ may be a curated prediction table whose rows define future prediction queries (such as forecasting revenue for an entity in the next quarter). When either task is temporal, the context is restricted to rows available before the prediction time. 

In-context learning for prediction tasks. In a classical in-context learning approach, fθ predicts the target column c⋆ for a query row r by conditioning on a support set Sr of labeled rows from the target table T ⋆. Each support row i ∈ S r has an observed target value yi = xi,c ⋆ . A local relational context Ci is then constructed around each support row and a context Cr around the query row r (with its target value masked). The model fθ predicts yr using the support and query context as: 

ˆyr = fθ ({(Ci, y i) : i ∈ S r }, Cr ) . (1) Here, in-context examples are sampled explicitly as labeled rows, and each example is represented by its own relational context. However, support rows often retrieve overlapping cells through primary– foreign key links. For example, labeled rows for people who purchased the same shoe after seeing the same advertisement may include the same cells from the shoe table in their contexts. This duplication consumes the context budget and limits the number of examples in context. 3Context window of relational transformers. RT [23] instantiates the context preparation idea differently. Rather than separately sampling support rows and constructing an independent context around each one, RT samples a single query-centered context Cr around the query row r (see stage (4) in Figure 1). This context is obtained by expanding from r along primary–foreign key links while keeping yr masked. During this expansion, the context may naturally include other rows from the target table whose target values are observed. Thus, the support examples are not sampled separately. They are induced implicitly by the relational context around the query row. Therefore, the prediction of an RT model is given by ˆyr = fθ (Cr ). The benefit is that overlapping relational neighborhoods are represented only once inside a single query-centered context, rather than being duplicated across independently sampled support examples. 

Masked token prediction with relational transformers. RT treats each cell in Cr as a token and predicts the masked target cell with a masked token prediction objective. Thus, heterogeneous prediction tasks are reduced to a common ‘cell prediction’ problem over any database in a schema-agnostic manner. RT computes the input token embedding by combining the cell value, datatype-specific information, and frozen text embeddings of the corresponding table and column names. During the forward pass, each transformer block of RT applies three attention layers [26] in sequence: (1) column attention , where tokens attend within the same column, (2) feature attention , where tokens attend within the same row, and (3) neighbor attention , where tokens attend across rows connected by primary–foreign key links. This attention structure enables information sharing across rows, columns, and tables while preserving the relational structure of the database. See Appendix F for details. 

3 THE JOIN : A Large-Scale Pretraining Corpus of Relational Data 

Existing collections of relational datasets, such as RelBench [24, 29], CTU [25], BIRD [30], and Spider [31, 32] comprise diverse databases but fail to capture the structural and distributional variety of predictive tasks needed for training RFMs. To address this issue, we introduce THE JOIN , a corpus comprising 639 relational databases across diverse domains (e-commerce, sports, media, finance, healthcare, etc.) and 6K forecasting tasks spanning various levels of difficulty, including rare events and cold-start entities. We follow a four-stage approach to curate the corpus: (1) collection of raw databases from the web, (2) standardization of data types in tables, (3) task generation using LLMs, and (4) task filtering using an XGBoost model. See Appendix D for details. 

3.1 Collection 

We collected the raw data from five disjoint source classes: (1) curated relational repositories (CTU, OGB, OpenAlex), (2) public APIs (SEC EDGAR, CFPB, World Bank, EIA), (3) domain specific portals (Lahman, ATP, StatsBomb, Cricsheet, OpenFlights), (4) community dumps (Stack Exchange), and (5) benchmarks (Kaggle, Spider/BIRD). Every contributing source is either a bulk archive published under a permissive license or a public API whose published terms permit programmatic research use. The classes carry qualitatively different relational structures: CTU schemas are small, clean, and follow third-normal-form, whereas Stack Exchange dumps are wide and denormalized. As a preliminary quality filter, we only collect databases that have at least two tables joined by a foreign key, and at least one column that can be parsed as a timestamp. Table 4 lists the domains included in the corpus. To avoid contamination, we exclude databases that overlap with ones in RelBench [29], RelBench v2 [24] and 4DBInfer [33] using source identity rather than schema similarity. 

3.2 Standardization 

The databases collected in their raw form are usually messy, with inconsistencies across column data types, timestamps, and primary-foreign key links being the major issues. For example: natively boolean columns are represented as strings "true" /"false" , dates are represented as ISO strings, and foreign keys exist only as a column-naming convention with no explicit declaration. To address such issues, we apply five idempotent detector-and-transformer fixes that recover the canonical relational structure: (1) boolean coercion , rewriting string and uint8 columns whose values fall within a canonical truth-set as booleans, (2) numeric coercion , casting string-encoded numerics to integers or floats with an identifier blacklist guarding zip codes and ISBNs, (3) foreign-key inference 

by name match plus an ≥ 80% value-containment test against parent primary keys, (4) temporal 

4normalization , electing a single time column per table from regex, name-hint, and integer-year candidates; and (5) entity-axis subsampling of oversized databases, retaining all activity rows for sampled entities to preserve their full activity histories. 

3.3 Task generation 

While cell imputation tasks are naturally defined by simply masking a cell/column in an existing database, in forecasting tasks the target cell/column (e.g., revenue next month) does not appear in the database and has to be explicitly generated. To obtain forecasting tasks we proceed as follows. 

Audit and eligibility. Each database is first parsed into a typed schema graph with two named roles: an entity table (whose primary key is referenced by a foreign key (FK) from another table, identifying a long-lived object such as a customer, player, or hospital) and an activity table (with both a timestamp column and an FK to an entity table, so each row is a timestamped event attributable to an entity). A database is marked as eligible for task generation if it has at least one entity table, at least one activity table, ≥ 5 unique timestamps in that activity table, and ≥ 100 rows. The first two conditions ensure the schema can express a per-entity forecasting task. The timestamp and row count conditions allow us to perform XGBoost-based filtering of the generated tasks for quality control. 

Propose and generate. Proposing forecasting tasks for a database requires subject-matter expertise and a scalable way to verify correctness. We use an LLM (Claude Opus 4.6) for the former and a lightweight deterministic checker for the latter. For every eligible database, the LLM is given the schema description in text and is asked to write a set of task proposals in JSON. Each proposal selects one of 25 registered template families, grouped into eight reasoning regimes. These include 

aggregation , threshold/existence , trend/change , behavior/churn , ranking , adoption/novelty , streak ,and tail-event tasks. The checker then iterates through each proposal and drops it if: (1) a referenced column does not exist, (2) the entity column is not a foreign key, or (3) the requested pattern is not one of the registered templates. The LLM proposer is run multiple times per database, where each pass sees the tasks already accepted and is asked specifically for templates with low coverage. 

3.4 Task filtering 

Finally, we score each task using an XGBoost model over window-aggregation features. We retain tasks that are either learnable , where XGBoost beats the lightweight historical baselines, or where the signal is too weak for these baselines but still act as harder learning objectives for stronger models. Overall, this process gives us 6,023 forecasting tasks, where each task is defined by its description and a table with timestamped labels (e.g., future revenue for each quarter) 1. See Appendix D for case studies and a manual audit of the tasks for their practicality and realism. 

4 Pretraining Recipe 

Here we describe our key improvements to the pretraining recipe of the original RT paper [23], which enable large-scale pretraining and context-efficient predictions (Figure 1). 

4.1 Long-context training 

The context size L is the number of cells presented to RT and is a key scaling axis to improve prediction quality. However, training at large L is computationally expensive. Further, the same pretrained model should be able to handle both small and large contexts at test-time, so that inference compute can be traded off against quality. Hence, we train at a mix of context sizes. For each training batch, we sample L ∼ Unif( L) from a fixed set L of context sizes. We keep batch size B

constant irrespective of L for stable optimization. As GPU memory scales as L × B, we use gradient accumulation adaptively to prevent out-of-memory (OOM) errors at large L.

54.2 Retrieval 

The original RT recipe [23] samples the relational context Cr with a bounded-width breadth-first search (BFS) over primary and foreign key links starting from the target row r. As the context length 

L grows, BFS can exhaust the local neighborhood, retrieve less relevant rows, and miss useful support rows from the target table. Retrieval is especially important for relational data because contexts are heterogeneous. For example, when predicting whether a user will click on a shoe ad, plain BFS may spend the context budget on generic user history or similar product cells. We use a two-stage sampling approach based on random walks to first retrieve similar rows and then expand the local neighborhood of each such row to prepare the context. Our approach can hence prioritize nearby target rows repeatedly reached through shared users, shoes, and ads tables for high quality contexts. 

Stage 1: Random-walks for global retrieval. The first stage uses random walks inspired by Pixie [34] and PinSAGE [35]. We run W random walks of length K from the target row r and record visit counts for rows in the target table T ⋆. We rank these rows by visit count, optionally using timestamps when the recency bias parameter ρ is set to 1. The walk parameters W and K

approximate the random-walk ordering efficiently and are tuned for latency. Unlike vector-similarity retrieval, this sampler requires no pre-computation and can run on the fly across large databases in a highly parallelizable manner. For example, we use W = 10 ,000 random walks, each of K = 20 

steps, with zero data loading overhead as the context sampler running on the CPU is ready with the next batch before the forward and backward passes have completed on the GPU. While random walks add a small latency overhead at test-time, our sensitivity analysis in Appendix I shows that lower values of W and K reduce this overhead significantly while largely retaining accuracy. 

Stage 2: BFS for local retrieval. For the second stage, we use the ranked rows as seeds for local BFS with context size ℓ and width bound b until the total context size reaches L. The full procedure is given in Algorithm 1 (Appendix I). Along with L, the retrieval parameters (ℓ, b, ρ ) can be tuned at test time. To allow for this, we need to expose the model to diverse contexts during training. Hence, we randomly sample (ℓ, b, ρ ) ∼ Unif( Lℓ × B × R ) using the values listed in Section 5. 

5 Pretraining Results 

Pretraining details. We use an 86 M-parameter RT model with 12 layers, 512 hidden size and 8 attention heads, incorporating the improvements of [26] (such as QK-Norm) over the original architecture of [23]. During pretraining, we sample context size L from L = {512 , . . . , 8192 }, the local context size ℓ from Lℓ = {128 , . . . , 8192 }, the BFS width-bound b from B = {8, . . . , 256 } (all powers of two) and the recency parameter ρ from R = {0, 1}, and mask only the target cell (see Appendix H for experiments with multi-cell masking). We pretrain in two phases, first on the synthetic PluRel corpus [26] ( 86 ,211 tasks over 1,900 

databases) 2 and then on 13 ,243 tasks from a 523 -database subset of THE JOIN (excluding the largest DBs due to memory bottlenecks). We optimize with Muon [36] at a constant learning rate after warmup and select the best checkpoint after stochastic weight averaging (SWA) [37] as recommended by Ranjan et al. [38]. The same checkpoint is used for all classification and regression tasks. Each phase takes about a day on a single node with 8×A100 GPUs. See Appendix G for details. 

Evaluation. We evaluate on RelBench [29], which comprises 21 forecasting tasks across 7 databases (9 regression and 12 binary classification tasks). These tasks span rare-event, cold-start, heavy-tailed and long-horizon regimes (see Appendix E for task descriptions). All databases used at evaluation are held out from pretraining. Following the official RelBench leaderboard, we use Z-score normalized mean absolute error (nMAE, lower is better) for regression and AUROC (higher is better) for classification tasks and report the average metrics.

6.2 Context ensembling 

Both the random-walk retrieval and the bounded-width local BFS stages of our context sampler are stochastic, with different random seeds yielding different yet equally viable contexts. Context ensembling simply averages the predictions made from nens independently sampled contexts. En-sembling reduces prediction noise due to retrieval by averaging over contexts and can be computed in parallel across nens . We sweep over nens ∈ { 1, 2, 4, 8, 16 } using different sampler seeds with a default configuration of L = 8192 , ℓ = 256 , b = 32 , ρ = 1 and showcase the benefits.

These observations highlight that RT-J has evidently absorbed world knowledge attached to real table and column names during pretraining on THE JOIN .

7.2 Alternatives to random-walk retrieval 

We compare our random-walk retrieval approach (Section 4) against five alternatives at inference: uniformly random task-row selection, BFS of width {32 , 256 } rooted at the target (the original scheme of [23]), and two vector-similarity retrievers that score task rows by RDBLearn features or 

RT-J embeddings. In particular, the RT-J embedding of a task row is the final hidden state at its masked target cell, computed over a 256 -cell BFS context around the row. Both similarity retrievers rank labeled task rows dated before the target by cosine similarity and use them, in that order, as seeds for the same local BFS as random-walk retrieval.

8 Discussion and Conclusion 

Our results show that RT-J can make accurate predictions on new datasets with as few as a hundred examples, in a single forward pass. This makes it practical to solve a wide range of predictive tasks without building dedicated feature engineering pipelines, or relying on extensive labeled data. Examples include flagging likely churn or fraud in a small-scale enterprise without a large customer base; predicting outcomes of novel clinical trials with small cohorts; and answering one-off predictive questions from an analyst. RT-J could be exposed directly in the database system, allowing users to request quick ad-hoc forecasts without an expensive labeling step. It could also be offered as a tool for LLM agents to call when a question requires predicting an unknown value, unlike transforming existing ones with SQL. THE JOIN is a first step toward capturing the immense diversity of real-world applications of relational foundation models (RFMs) like RT-J . Beyond synthetic pretraining corpora prevalent for structured data foundation models, THE JOIN offers hundreds of real databases across science, healthcare, finance, sports, etc., with semantically meaningful predictive tasks spanning rare-event, cold-start, heavy-tailed and long-horizon regimes. 

Conclusion. We developed a pretraining recipe for relational transformers (RTs) [23] with long-context training, random-walk retrieval of high-quality in-context examples, and test-time compute scaling via context tuning and ensembling. With this recipe, we obtain RT-J by first pretraining on PluRel [26] synthetic data and then on THE JOIN , our large-scale real data corpus. RT-J matches strong feature engineering pipelines with as much as 10 × fewer examples. Experiments highlight the role of real data pretraining, schema semantics and context engineering. Our work moves RFMs closer to practical systems that can solve novel predictive tasks over databases on the fly. 

Limitations and future work. RT-J has been trained up to 8,192 context cells; future work can explore efficient longer context training, which would allow both for more in-context examples, and larger relational contexts for them. RT-J is unable to solve link prediction and recommendation tasks, sharing this limitation with RT [23]. Our evaluation is limited to RelBench, with only 21 

tasks on 7 databases—inspired by THE JOIN , future work can expand the scope of real-world relational benchmarks. We release (1) the RT-PluRel and RT-J models, (2) THE JOIN data, (3) the LLM agent task curation pipeline, and (4) our pretraining, finetuning and inference code at

B Other Relational Foundation Models 

Beyond the pipelines of Section 5, we looked into comparing RT-J with recent relational foundation models (RFMs), but none could be evaluated under our protocol, in which every method sees the same in-context examples. 

KumoRFM [10]: closed weights, and API access does not allow controlling the in-context examples, precluding a fair comparison. 

KumoRFM-2 [11]: closed weights. API access was released only a few weeks before our submission deadline, and no longer works due to the ongoing migration of Kumo to NVIDIA. 

Griffin [22]: the released checkpoints are incapable of in-context learning, and pretraining Griffin with our recipe is not feasible, as the recipe is engineered around transformer-based architectures, which Griffin is not. 

RDB-PFN [28]: supports only classification tasks, whereas our evaluation covers both regression and classification. 

TabPFN-Rel with TabPFN-3 and TabPFN-3.5 [15, 16]: released after submission. 17 C Related Work 

Relational deep learning and benchmarks. Relational deep learning (RDL) is a machine learning paradigm that operates directly on relational databases, avoiding the need to manually flatten a database into a single feature table [6]. A common formulation represents a database as a heteroge-neous relational entity graph: rows are nodes, tables define node types, and primary–foreign-key links define typed edges [29]. Graph neural networks can then propagate information across related rows and tables, enabling end-to-end prediction over multi-table data [7, 29]. Recent work has improved the efficiency and expressiveness of relational message passing [7], and transformer-based relational architectures have also been proposed [8, 9]. Kanatsoulis et al. [40] introduce an efficient positional encoding framework based on lightweight message-passing operations, providing structural features that have been shown to improve relational deep learning models. Broader surveys and position papers frame these models as part of a larger agenda for relational deep learning [41]. Benchmarking has been central to this progress. RelBench [29] introduced a standardized suite of relational prediction tasks, while 4DBInfer [33] and RelBench v2 [24] expand the scale and diversity of relational benchmarks, including broader task families and database domains. These benchmarks make it possible to compare relational models under realistic multi-table and temporal constraints. 

Relational foundation models. Recent work has begun to develop foundation models specifically for relational data. These models seek to transfer across schemas and tasks rather than training a separate predictor for every database. KumoRFM and KumoRFM-2 study in-context learning for relational data at scale [10, 11]. Griffin develops a graph-centric relational foundation model for transfer across relational databases [22]. The Relational Transformer (RT) takes a complementary cell-level approach: database cells are treated as tokens, schema semantics are included in the input, and relational attention masks encode primary–foreign-key structure [23]. PluRel [26] enables RT pretraining with synthetic data. It synthesizes multi-table databases from scratch, including schemas, primary–foreign-key links, and feature distributions, enabling controlled studies of synthetic data scaling for relational foundation models. Our work builds directly on RT because its cell-level formulation is well-suited to context-efficient relational prediction. Labeled task rows, unlabeled rows, schema metadata, and linked evidence can all appear in the same context window, making masked cell prediction a natural interface for both pretraining and inference. However, the original RT work primarily establishes a schema-agnostic architecture; it does not develop a scalable pretraining and inference recipe. We therefore use RT as the backbone and study how to make it effective when only a small number of in-context examples are available. 

Tabular foundation models and relational tabularization. Tabular foundation models aim to bring pretraining and in-context learning to single-table prediction. TabPFN and its successors show that transformers can perform strong in-context prediction when labeled rows from a tabular task are provided in the context [17, 18]. More recent models, including TabICLv2 and other large-scale tabular foundation models, extend this paradigm to larger datasets, richer feature spaces, and broader tabular distributions [19, 20, 42, 43]. These methods provide strong evidence that structured prediction can benefit from foundation-model-style training. Relational databases, however, contain structure that is not present in ordinary single tables. Predictive evidence may lie several joins away from the target row, and the relevant signal may involve temporal histories, linked entities, or multi-hop dependencies. One way to use tabular foundation models in this setting is to first transform the database into a single feature table. RDBLearn follows this strategy by aggregating relational neighborhoods into engineered features and then applying a tabular in-context learner [21]. This approach is effective and provides a strong baseline, but the flattening step changes the input representation: the model no longer reasons directly over cells, schemas, timestamps, primary–foreign-key links, or multi-table structure. 

Large language models for relational data. Another line of work applies large language models to structured and relational data by serializing tables or database neighborhoods into text [44]. This has the advantage of using powerful pretrained language models without designing a specialized architecture. However, serialization can be inefficient and brittle. Relational structure must be expressed as text, long database contexts can exceed the model context window, and the resulting input 18 format may differ substantially from the data distribution seen during language-model pretraining. Hybrid approaches that combine graph or relational encoders with LLMs can partially address these issues, but they often still depend on task-specific components or limited context construction [45]. 

Graph foundation models. Several papers have paved the way toward graph foundation models. Mole-BERT [46] pretrains GNNs with masked atom prediction and triplet-based contrastive learning for node- and graph-level drug-discovery tasks. Beaini et al. [47] further show that molecular pre-training benefits from scale, using large multi-task datasets with billions of labels and demonstrating that combining quantum and biological supervision improves low-resource performance. Recent work has extended pretraining graph models beyond molecules. PRODIGY [48] introduces prompt-based graph representations for in-context learning. GraphAny [49] studies zero-shot node classification across graphs with disjoint feature and label spaces, using LinearGNN ensembles and inductive attention inspired by linear least-squares estimation. ULTRA [50] learns transferable relational representations for zero-shot reasoning over unseen knowledge graphs. GraphGPT [51] converts graphs into reversible token sequences using Eulerian paths, enabling scalable generative Transformer pretraining for graph-structured data. Most recently, Bechler-Speicher et al. [52] scale the graph foundation model paradigm to heterogeneous billion-scale graphs, proposing a billion-parameter Transformer architecture and a recipe for link prediction pretraining. 

D Additional Details on THE JOIN 

D.1 Agentic execution 

Constructing THE JOIN corpus manually would require months of human engineering, particularly for web collection as each source presents different download mechanisms, file formats, schema conventions, parsing failures, and data-quality issues. We therefore used Claude Code agents as the execution layer for corpus construction. The agents identify and inspect candidate sources, implement and debug domain-specific collectors, adapt standardization routines to newly observed edge cases, run the pipeline, inspect logs and intermediate artifacts, and iterate until each stage reaches its completion criteria. The agents were used for engineering and orchestration, while task validation, scoring, filtering, baseline computation, loadability checks, and provenance tracking were performed by deterministic scripts based on human-defined criteria. 

D.2 Phase 1: Collection Collecting from heterogeneous sources. The first phase builds a raw relational snapshot from a broad set of public data sources. This is difficult to automate with a single scraper because different sources expose data in very different ways: as SQL dumps, SQLite databases, CSV bundles, parquet or JSON exports, archive mirrors, or paginated APIs. We therefore use source-specific collectors. Each collector downloads the data, parses it in its native format, recovers table and key metadata when available, and converts the result into a common parquet-based representation. We also exclude databases that exactly overlap with established benchmark sources in RelBench, RelBench v2 and 4DBInfer, using source identity rather than schema similarity as the criterion. 

Respecting upstream constraints. The collectors are designed to be reproducible while remaining respectful of the sources. API-based collectors follow the documented rate limits and include the required identifying information. Bulk-download sources are handled at the archive level, and for sources that publish periodic snapshots, the refresh cadence of our corpus is limited by the cadence of the upstream release. 

Normalizing the collected data. Before any database is passed to later stages, the collector performs basic normalization. For example, (1) primary and foreign keys are converted to integer indices, (2) timestamps and booleans are stored in consistent types, and (3) mixed-type columns are either normalized or rejected. We also store primary-key, foreign-key, and time-column metadata alongside each Parquet table, so that downstream stages do not rely on source-specific assumptions. D.3 Phase 2: Standardization Creating a common representation. After collection, each database is standardized into a uni-form relational format. The purpose of this stage is to make heterogeneous sources loadable and comparable, without altering their semantic content. Each fix is implemented as an idempotent detector–transformer pass over the collected parquet files: a pass first checks whether the target invariant already holds, and only rewrites the data when needed. 

Recovering relational structure. Many public datasets contain useful structure that is implicit rather than declared. We therefore recover primary keys, foreign keys, time columns, boolean fields, and numeric columns when they can be inferred reliably. These repairs are conservative: candidate keys must satisfy uniqueness checks, foreign keys must pass containment checks, and identifier-like fields such as zip codes, ISBNs, phone numbers, and barcodes are not coerced into numeric values. 

Normalizing common type issues. The standardization pass resolves common inconsistencies across sources, such as booleans stored as strings, dates stored in mixed textual formats, year columns stored as integers, and numeric values stored as strings. Ambiguous cases are left unchanged or flagged rather than silently modified. This keeps the downstream interface simple while avoiding brittle source-specific assumptions. 

Controlling scale. For databases that are too large for repeated downstream processing, we apply deterministic entity-axis subsampling: entities are sampled with a fixed seed, all associated activity rows are retained, and keys are reindexed to preserve relational consistency. 

Preserving auditability. All standardization fixes are performed by mechanical scripts, and each transformation is governed by explicit rules. As a result, downstream task generation and evaluation operate on a consistent representation, while every repair remains reproducible and inspectable. 

D.4 Phase 3: Task proposal and validation Proposing tasks from schema context. For each eligible database, the proposer receives a structured summary of the database, including its domain, tables, row counts, key relationships, time columns, column types, basic column statistics, and a small number of example rows from activity tables. This context is wrapped in a fixed prompt that specifies the allowed task templates, the required JSON format, and the validation rules. The proposer also receives the names of previously generated tasks for that database, which helps reduce duplicates across passes. 

Constraining the proposal space. Task proposals are restricted to a registered set of templates, listed in Table 5. This keeps the generated tasks interpretable and mechanically checkable, while still allowing broad coverage across domains. Proposals that refer to unknown templates are rejected before further processing. 

Validating mechanically. The LLM proposes candidate tasks, but acceptance is decided by a deterministic validator. The validator checks that referenced tables and columns exist, entity columns are valid foreign keys, numeric fields are used where required, generated target names do not collide with existing columns, task names follow the required format, and binary thresholds avoid trivially imbalanced labels. Rejected proposals are logged with their failure reason and are not written to the released task set. 

Improving diversity across passes. Each database is processed through multiple proposal passes. Early passes tend to recover natural or obvious tasks for the schema, while later passes explicitly target under-represented templates and harder prediction settings, such as rare positives, cold-start behavior, heavy-tailed regression, ranking, and derived-ratio tasks. This multi-pass strategy increases task diversity while preserving the same mechanical validation standard for every accepted proposal. 22 Keeping generation auditable. The proposal stage uses an LLM to suggest candidate tasks, but the final task set is determined by explicit templates and deterministic checks. This separation allows the pipeline to benefit from the LLM’s ability to identify plausible prediction problems from heterogeneous schemas, while keeping task inclusion reproducible, inspectable, and independent of unverified free-form judgments. To keep the pass scalable, training is capped at 5,000 rows per task and evaluation at 2,000 rows per task. Filtering and difficulty assignment. The quality filter removes tasks that are unlikely to be useful for downstream evaluation, such as tasks that are nearly trivial, exhibit severe distribution drift, or fail during baseline fitting. Tasks with non-trivial baseline signal are retained, and we also retain non-trivial tasks for which XGBoost does not recover signal, since stronger relational models may still exploit structure missed by the lightweight baseline. Retained tasks are assigned a coarse difficulty level from their XGBoost score: easy, medium, or hard. 

Preparing the release format. After loadability validation, each task is converted into the release format. The train, validation, and test splits are concatenated in chronological order into a single time-ordered training file, while preserving the schema metadata required by downstream loaders. 

D.6 Asset licenses, Citations, and Compliance Compliance practice. Every contributing source is either (a) a bulk archive that the upstream provider publishes for download under an explicit license, or (b) a public API whose documented terms permit programmatic research use. We do not crawl arbitrary websites, do not bypass paywalls, do not ignore robots.txt , and do not scrape sources whose terms of service forbid automation. 

Released-corpus license. We intend to release the corpus under CC-BY-SA 4.0 . Per-database metadata records (i) the upstream source identifier, (ii) the upstream license string verbatim, and (iii) any usage restrictions inherited from the source (e.g. non-commercial-only for ATP-Tennis, StatsBomb, Yelp, FMA, and ListenBrainz; research-use-only for the CTU repository). Downstream users redistributing derivative works must honor those per-source restrictions in addition to the aggregated CC-BY-SA 4.0 license on the corpus assembly. 

PII. The corpus contains no personally-identifying information beyond what each upstream source has already published under its own license. Where source data uses pseudonymized identifiers (e.g. Stack Exchange user IDs, Lahman player IDs), we preserve those identifiers verbatim and do not attempt to de-anonymize or join across sources.

G Pretraining Details 

In all our experiments we use an 86 M-parameter RT model with 12 layers, 512 hidden size and 8 attention heads, incorporating the improvements of [26] (such as QK-Norm) over the original architecture of [23]. We sample context size L from L = {512 , 1024 , 2048 , 4096 , 8192 }, the local context size ℓ from Lℓ = {128 , 256 , 512 , 1024 , 2048 , 4096 , 8192 }, the BFS width-bound b from 

B = {8, 16 , 32 , 64 , 128 , 256 }, and the recency parameter ρ from R = {0, 1}. The random-walk retriever uses W = 10 ,000 walks of length K = 20 , and only the target cell is masked ( pmax = 0 ). We pretrain in two phases: first on the synthetic PluRel corpus [26] ( 86 ,211 tasks over 1,900 

databases), then continuing from that checkpoint on a fixed mixture of 13 ,243 THE JOIN tasks drawn from the 523 databases whose preprocessed on-disk footprint stays under 5 GB. Each phase is early-stopped once neither mean validation AUROC nor mean validation nMAE (of the live or SWA weights) has improved for 10 K optimizer steps (at 18 K steps for PluRel and 26 K for THE JOIN ), at a global batch size of 1024 contexts per step using Muon [36] for 2D weight matrices and AdamW for the remaining parameters, at a constant learning rate of 5 × 10 −4 (RMS-matched for Muon as in [53]) after a linear warmup over the first 2000 steps. To compensate for a lack of decay phase [54], and following the recommendation in [38], we track the stochastic weight average (SWA) performance during training and select the best SWA checkpoint based on validation performance. Specifically, we use an exponential moving average (EMA) for SWA, with momentum 0.9995 , which gives an effective window of ≈ 2000 steps, and find that it produces more stable curves with better results. Each phase takes about a day or less on a single node with 8×A100 GPUs, with BFloat16 activations and FP32 master weights [55]. The released RT-J checkpoint is the SWA weights after 9K steps of the THE JOIN phase, selected by mean validation AUROC ( 74 .36 ); selection runs over the whole SWA trajectory, so the selected step lies well before the step at which the phase stopped. The same single checkpoint is used for every task, classification and regression alike.

I Random-Walk Context Construction 

This appendix gives the full procedure for context construction summarized in Section 4. For one task item, we score same-table candidate rows by random-walk visit counts (Stage 1), then consume the candidates in order—most recent first with visit counts breaking ties when the recency flag ρ = 1 ,or by visit count alone when ρ = 0 —as launch points for the width-bounded BFS cell collector BFSC OLLECT of the original RT, which we reuse unchanged (Stage 2). Walks step uniformly at random along PK and FK edges, restricted to neighbor rows whose timestamp does not exceed the target’s timestamp t⋆; this enforces temporal validity at the walk level and avoids leaking future information into the context. Only visits to rows other than the target in the target’s table τ contribute, so the score ranks same-table rows by their personalized random-walk proximity to the target. 

I.1 Sensitivity to random-walk parameters 

The random-walk retriever of Appendix I uses W = 10 ,000 walks of length K = 20 by default. We evaluate RT-J with the default and three cheaper settings on the 8192 -row test subsample at L = 8192 ,32 over three context seeds. Table 9 breaks down the per-example inference cost and Tables 10 and 11 the accuracy. Fewer or shorter walks cut the context-sampling cost from 28 .1 to 14 .3–17 .9 ms per exam-ple, while the forward pass stays at about 10 ms. Classification degrades steadily as the walks shrink, from 72 .9 to 71 .9 mean AUROC, driven by rel-trial/study-outcome (59 .4 to 52 .7–55 .8), 

rel-stack/user-engagement and rel-f1/driver-dnf . Regression is insensitive on average (33 .3–33 .6 mean nMAE), although individual tasks move in both directions: rel-hm/item-sales
