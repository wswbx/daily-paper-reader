## 摘要
LLM智能体越来越多地通过命令行和基于CLI的工具接口解决本地任务，包括代码编辑、仓库检查、数据分析以及文件工作流。现有评估通常强调任务成功率，但部署的本地智能体并非仅由模型构成：CLI中介了提示、上下文回放、工具输出、文件访问、终端观测以及停止行为。因此，相同的模型在不同CLI下可能产生不同的成功率、令牌消耗和成本特征。我们提出AGENTMETER，一个用于评估CLI中介的本地任务求解智能体中模型-CLI匹配的基准，同时引入AgentMeter评分（AMS），一种以成功率为锚点、考虑成本并基于校准任务努力等级的度量。AgentMeter使用Benchmark90作为完整验证集，Core30作为低成本子集，用于跨24个完整模型-CLI配置的扩展比较。在Core30上，常见部署标准选择不同配置：最高Pass/30选择GLM-5.1与qwen-coder，最低Tok./Pass选择GPT-5.3-Codex与kimi-cli，最低计费美元/Pass选择Qwen3.6+与Codex，而最高AMS选择Qwen3.6+与kimi-cli。Benchmark90验证保留了Top-1配置和Top-3集合，Spearman相关性0.765，Kendall相关性0.567，AMS平均绝对误差0.0383。这些结果表明，模型选择和CLI选择不应解耦，模型-CLI配置应作为部署单元进行评估。

## Abstract
LLM agents increasingly solve local tasks through command-line and CLI-based harness interfaces, including code editing, repository inspection, data analysis, and file workflows. Existing evaluations often emphasize task success, but deployed local agents are not models alone: the CLI mediates prompts, context replay, tool outputs, file access, terminal observations, and stopping behavior. As a result, the same model can produce different success, token, and cost profiles under different CLIs. We introduce AGENTMETER, a benchmark for evaluating model-CLI matching in CLI-mediated local task-solving agents, together with AgentMeter Score (AMS), a success-anchored, cost-aware metric over calibrated task-effort tiers. AgentMeter uses Benchmark90 as the full validation set and Core30 as a lower-cost subset for expanded comparison across 24 complete model-CLI configurations. On Core30, common deployment criteria select different configurations: highest Pass/30 selects GLM-5.1 with qwen-coder, lowest Tok./Pass selects GPT-5.3-Codex with kimi-cli, lowest billable USD/Pass selects Qwen3.6+ with Codex, while highest AMS selects Qwen3.6+ with kimi-cli. Benchmark90 validation preserves the Top-1 configuration and Top-3 set, with Spearman correlation 0.765, Kendall correlation 0.567, and AMS MAE 0.0383. These results show that model choice and CLI choice should not be decoupled, and that model-CLI configurations should be evaluated as the deployed unit.

## 1. 核心问题与整体含义（研究动机和背景）

- **核心问题**：当前LLM智能体通过命令行接口（CLI）执行本地任务（如代码编辑、仓库检查、数据分析）时，评估常聚焦于模型本身的任务成功率，忽略了CLI作为中介层对模型行为的影响。同一模型在不同CLI下，由于提示布局、上下文回放、工具输出序列化、文件访问方式、终端观测和停止策略的差异，会产生不同的成功、令牌消耗和成本特征。因此，模型与CLI的匹配不是中性的，需要作为部署单元整体评估。
- **研究动机**：现有基准（如SWE-bench、Terminal-Bench、AgentBench）虽评估智能体能力，但通常视CLI为固定包装，未将模型-CLI配对作为独立变量；成本导向的研究（如路由、缓存）仅关注组件效率，缺乏端到端的部署效用度量。实际部署中，不同标准（最高通过、最低token/通过、最低成本/通过）会选择不同的模型-CLI配置，而非单一模型最优。
- **整体含义**：提出AgentMeter基准和AgentMeter Score（AMS）指标，将模型-CLI配置作为评价单元，综合考虑任务成功、原始令牌消耗、计费成本及昂贵失败惩罚，揭示仅凭模型或仅凭CLI无法准确刻画部署效用的现象。

## 2. 方法论：核心思想、关键技术细节与算法流程

- **核心思想**：以成功率为锚点，在分层的任务努力等级（Easy/Medium/Hard）内融合成本效率，并惩罚昂贵失败。AMS是三个层级得分的均值，每层级得分由任务质量、成本预算质量（CostAUBQC）和昂贵失败率（EFR）组合而成。
- **关键技术细节**：
  - **任务努力等级校准**：对每个任务计算经验努力度 \(E_i\)，综合考虑通过率、平均奖励、令牌中位数、轮次中位数和交互脚印，通过公式（1）得到。然后将Benchmark90的90个任务均分为30个Easy、30个Medium、30个Hard。
  - **传统诊断指标**：保留Pass率、Tok./Pass（每通过任务的原始令牌数）、USD/Pass（每通过任务的计费美元成本），但指出单一指标不足。
  - **成本预算质量（CostAUBQC）**：对每个层级 \(g\) 定义预算网格 \(B_g\)，计算在预算 \(b\) 内的任务质量累计面积，见公式（3）（4）。预算网格由层级内成本分位数确定（表1）。
  - **昂贵失败率（EFR）**：对于未通过任务，若计费成本超过层级阈值 \(\tau_g\)（P90失败成本），则计入惩罚，见公式（5）。
  - **AgentMeter Score (AMS)**：每层级得分 \(\text{TierScore}_g = [\alpha \cdot \text{SR}_g + (1-\alpha) \cdot \text{CostAUBQC}_g] \cdot (1-\text{EFR}_g)\)，其中 \(\alpha=0.6\)。最终AMS = 三个层级得分的均值，见公式（6-8）。
- **算法流程**：
  1. 确定任务努力等级（基于Benchmark90先验校准，不依赖模型身份或AMS）。
  2. 运行每个模型-CLI配置在全部任务上，记录任务质量 \(R_i\)、通过标志 \(y_i\)、令牌消费 \(T_i\)、计费成本 \(C_i\)（按公式（2）计算，含缓存字段）。
  3. 对每个层级，计算SR、CostAUBQC和EFR，进而得TierScore。
  4. 计算AMS。
- **定价公式**：\(C_i = p_{in} N_i + p_{out} Y_i + p_{create} A_i + p_{hit} H_i\)，其中 \(N_i = (X_i - A_i - H_i)^+\) 为未缓存输入令牌。

## 3. 实验设计

- **数据集/场景**：
  - **Benchmark90**：90个本地任务，来自SkillsBench（代码与文件操作）、Terminal-Bench（终端任务）、DA-Code（数据分析编码），最终分为Easy/Medium/Hard各30个。
  - **Core30**：Benchmark90的子集，30个任务（10 Easy, 10 Medium, 10 Hard），用于低成本扩展比较，覆盖16个SkillsBench、9个Terminal-Bench、5个DA-Code任务。
- **Benchmark**：AgentMeter本身即提出的基准，无外部对比基准，但与传统诊断指标（Pass/30, Tok./Pass, USD/Pass）在同一配置上比较其选择差异。
- **对比的方法/配置**：
  - **模型**：Qwen3.6+、DeepSeek-v4-pro、GLM-5.1、MiniMax-M2.5、Claude Sonnet 4.6、GPT-5.3-Codex（共6个）。
  - **CLI**：Claude Code、Codex CLI、qwen-coder、kimi-cli（共4个）。
  - **完整配置**：6×4=24个模型-CLI组合（Core30主实验）。Benchmark90验证仅包含其中16个具有90任务完整运行数据的配置。
  - **评估指标**：Pass/30、Tok./Pass、USD/Pass、AMS。
- **评价协议**：每个模型-CLI-任务运行一次（最新完成的选择规则），失败轨迹仍计入令牌和成本。基础设施无效的尝试被排除。单次运行，未报告多轮方差。

## 7. 优点

- **创新问题定义**：首次提出模型-CLI匹配评价问题，指出CLI中介是影响部署效用的关键变量，而非固定包装。
- **评价指标综合且实用**：AMS同时考虑成功率、成本预算效率、昂贵失败惩罚，并通过任务努力层级校准使其对不同难度任务公平。
- **任务层级校准**：基于实证统计（通过率、奖励、令牌等）而非人工标注，减少主观偏差；且校准与最终评分使用不同证据（不含模型标识和AMS），防止信息泄露。
- **完整配置覆盖**：包含6个常见模型×4个主流CLI的完整网格，实验规模在同类研究中较大。
- **验证设置合理**：使用Core30进行扩展比较，Benchmark90作为验证集，且验证显示了排名稳定性，增强结论可信度。
- **公开实用工具**：提供了可执行的基准套件（Benchmark90和Core30）以及明确的评估协议。

## 8. 不足与局限

- **单次运行缺乏方差估计**：每个配置每任务仅一次尝试，无法评估偶然性和模型随机性，缺乏置信区间。
- **定价快照依赖**：成本基于特定日期的CNY价格和固定汇率，实际部署可能因折扣、缓存策略变化而变化，成本绝对值不通用。
- **基准任务覆盖有限**：仅涉及终端、数据分析和代码操作，未涵盖Web交互、多智能体协作、人机环等更广泛的智能体场景。
- **任务努力等级具有语境依赖性**：Easy/Medium/Hard标签基于当前Benchmark90校准池，对全新领域任务可能不适用；预算网格和阈值\(\tau\)也是固定的，改变可能影响排名。
- **超参数固定**：AMS中的\(\alpha=0.6\)为固定值，未做敏感性分析，不同\(\alpha\)可能导致不同排序。
- **缺少消融实验**：未单独验证预算质量、昂贵失败惩罚、层级校准对AMS的贡献；也未比较AMS与其他成本-成功组合指标（如F1-score与成本的合成）。
- **模型和CLI版本更新风险**：实验基于2026年6月的特定版本，模型更新或CLI变更可能导致结论变化。
- **可选运行选择规则**：尽管使用“最新完成”规则避免 cherry-pick，但多轮运行可能仍有选择性偏差。
