## 摘要
AI代理越来越多地通过框架在生产中运行，框架是LLM周围的软件，包含一个执行安全和有效性策略的引擎，例如'在提交前运行测试'。执行这些策略需要弥合语义鸿沟：策略意图用欠指定的自然语言表达，而执行必须作用于具体的系统动作，例如运行哪个测试。许多策略还定义了事件排序或数据流动作。然而现有方法存在不足。工具调用护栏会错过绕过工具层的系统动作，而操作系统沙箱控制资源访问而非动作，返回不透明的错误使代理困惑。我们的关键洞察是：策略上下文存在于最接近任务的代理中，而执行必须在操作系统层面进行以覆盖所有执行路径。我们引入ActPlane，一个策略引擎，允许代理声明策略并在操作系统内核中执行，提供语义反馈与隔离。ActPlane使用一个简单的信息流控制（IFC）DSL来支持跨事件策略。我们使用eBPF实现ActPlane，并在来自实证研究、编码任务基准和安全基准的策略上进行了评估。ActPlane提高了策略合规性，包括工具调用拦截无法观察到的间接执行路径，开销为1.9%至8.4%。ActPlane代码托管于https://github.com/eunomia-bpf/ActPlane。

## Abstract
AI agents increasingly run in production through harnesses, the software around the LLM, including an engine that enforces safety and effectiveness policies, e.g., 'run tests before committing.' Enforcing these policies requires bridging a semantic gap: policy intent is expressed in underspecified natural language, while enforcement must act on concrete system actions, e.g., which test to run. Many policies also define event ordering or data flow actions. Yet existing approaches fall short. Tool-call guardrails miss system actions that bypass the tool layer, while OS sandboxes control resource access instead of actions, returning opaque errors that confuse the agent. Our key insight is that policy context lives within the agent closest to the task, while enforcement must happen at the OS to cover all execution paths. We introduce ActPlane, a policy engine that lets agents declare policies and enforces them in the OS kernel with semantic feedback and isolation. ActPlane uses a simple information-flow control (IFC) DSL to support cross-event policies. We implement ActPlane with eBPF and evaluate it on policies from the empirical study, coding-task benchmarks, and safety benchmarks. ActPlane improves policy compliance, including on indirect execution paths that tool-call interception cannot observe, with 1.9%-8.4% overhead. ActPlane is at https://github.com/eunomia-bpf/ActPlane

## 1. 论文的核心问题与整体含义（研究动机和背景）

- **核心问题**：AI Agent在运行时需要执行安全和有效性策略（如“提交前先测试”），但现有机制存在**语义鸿沟**：策略意图以自然语言表达（模糊），而执行必须作用于具体的系统动作（如运行哪个测试命令）。同时，许多策略涉及事件顺序或数据流（跨事件策略），现有工具（工具调用护栏、OS沙箱）要么只拦截工具层调用（无法覆盖间接执行路径如子进程/脚本），要么控制资源访问而非动作（返回不透明错误，Agent无法理解）。
- **研究动机**：作者通过对64个包含`CLAUDE.md`/`AGENTS.md`的开源项目进行实证研究，发现83%的策略是系统可观测的，其中16%是跨事件策略（需要状态跟踪），且73.6%的策略需要项目或任务上下文才能实例化。现有方法无法同时满足“Agent可编写”、“OS级覆盖”、“跨事件跟踪”和“语义反馈”的需求。
- **整体含义**：提出ActPlane，一个可编程的OS级策略引擎，让Agent能声明策略，在内核层通过eBPF执行，提供语义反馈和隔离，弥合策略意图与系统动作之间的鸿沟。

## 2. 论文提出的方法论：核心思想、关键技术细节

### 2.1 核心思想
- **关键洞察**：策略上下文存在于最接近任务的Agent中，而执行必须在OS层面进行以覆盖所有执行路径（包括子进程、脚本等间接路径）。
- **设计原则**：
  - **Agent可写、OS可执行**：提供高层DSL供Agent生成具体规则，编译为确定性内核检查。
  - **安全隔离**：Agent不能削弱高层安全约束，不同Agent策略相互隔离。

### 2.2 关键技术细节

#### (1) 策略DSL（领域特定语言）
- 规则结构：`source → target operation → effect`，每个规则包含：源（exec/file/endpoint）、目标操作、效果（block/kill/notify）、可选时间门（temporal gate）、原因（语义反馈）。
- 示例：
  - 单事件：`block unlink "/data/**" if AGENT`（禁止删除数据）。
  - 跨事件：`kill exec "git" "commit" unless after exec "go" "test" exits 0 since write "**/*.go"`（提交前必须运行测试且测试通过）。

#### (2) 信息流控制（IFC）引擎
- 将源声明的标签附加到系统对象（进程、文件、网络端点），并在运行时通过OS数据流边（fork/exec/read/write/connect）传播标签。
- 标签单调递增（不可撤销，除非通过域层次解除），确保跨事件检查始终可用。
- 规则检查：基于当前主体的标签集、目标标签集、时间门条件决定是否触发效果。

#### (3) 层次化策略域（Hierarchical Policy Domains）
- 每个域对应一个进程树的运行时策略边界，子域继承父域所有规则，只能添加本地规则/标签/门，不能删除或削弱继承规则。
- 安全约束由高权限域加载，Agent可提交预编译的增量更新，内核中的权限检查器验证更新不违反继承规则。

#### (4) 实现
- 用户空间编译器/运行器（Rust，约3.2K行）和内核eBPF引擎（BPF C，约1.8K行）。
- 通过BPF-LSM拦截系统调用（exec/open/write/unlink/connect/fork/exit），标签用64位位掩码存储在BPF映射中，传播为按位OR操作。
- 支持最多128条并发规则。

## 6. 论文的主要结论与发现

1. **DSL覆盖率高**：Agent可基于自然语言策略生成所有607个OS可执行规则，首次编译成功率99.7%（2次重试后100%），成本仅$0.028/规则。
2. **决策合规率显著优于基线**：
   - ActPlane在190条轨迹上达到75.8% DCR，比Prompt-filter（48.4%）、Tool-regex（45.3%）、FIDES（48.9%）、无反馈IFC（53.7%）高22-31个百分点。
   - 优势集中在间接/隐藏执行路径（工具层无法检测），ActPlane检测率77.2%，基线仅34-40%。
3. **语义反馈关键**：ActPlane有反馈版本比无反馈版本（ActPlane-opaqe）多恢复3倍的违规（86 vs 27），反馈将检测转化为合规的成功率达97.7%。
4. **安全任务防护**：在361个OpenAgentSafety任务中，ActPlane阻止了74%的基线不安全行为，仅28个未阻止（主要属于聊天语义伤害、文件内容伤害或服务端协议未覆盖）。
5. **低开销**：
   - 端到端：Agent轨迹回放1.9%，内核编译6.5%（32条规则），最高8.4%（100条规则）。
   - 单系统调用：fork/exec增加3-69μs，open增加1.2-13.4μs，相对LLM推理时间（2-10秒）可忽略。
6. **跨模型稳定性**：使用不同模型（Qwen vs DeepSeek）排名一致（κ=0.822-0.920），确定性系统（ActPlane）稳定性高。

## 7. 优点：方法或实验设计上的亮点

- **解决实际问题**：实证研究揭示了现有方法无法覆盖的间接执行路径和跨事件策略问题，ActPlane直接针对这些缺口设计。
- **创新性整合**：将OS级eBPF与信息流控制（IFC）结合，既保持低开销又支持跨事件策略，不同于传统工具层IFC或纯资源控制沙箱。
- **Agent友好的DSL**：语法接近自然语言，Agent可自动生成，且支持语义反馈（告知Agent违反了什么规则、如何修复），降低人工编写成本。
- **安全隔离设计**：层次化策略域确保Agent不能削弱高层约束，运行时更新需通过内核权限检查。
- **实验全面**：覆盖策略生成、执行效果、开销、真实任务、安全防护多个维度，且进行了消融和跨模型验证。
- **开源**：代码已公开，可复现。

## 8. 不足与局限

- **覆盖范围有限**：仅处理45%的策略（单事件+跨事件），内容类策略（如代码风格）需交给linter和静态分析器，未集成。
- **OS级盲区**：无法检测服务端内部操作（如WebDAV上传、数据库突变）和纯聊天语义行为（无系统调用）。
- **错误率**：仍有7%的违规未检测（主要因翻译错误导致规则过窄），10%的误报（规则过宽）。虽可通过单次修订弥补，但人工干预仍可能必要。
- **可扩展性**：当前支持128条规则，较大部署可能需扩展；标签单调增加可能导致过度污染，虽提供新进程清理机制，但长期运行场景未充分评估。
- **实验局限性**：
  - RQ2的自定义基准未经第三方验证，评判器使用LLM可能引入偏差。
  - RQ4样本量小（21/217），结论推广需谨慎。
  - 未部署到多节点或云环境，未测试内核版本差异（仅Linux 6.15.11）。
  - 未与社区最新工具（如Tetragon、Crab）直接对比，尤其Crab也使用eBPF做Agent沙箱（论文中提及相关工作但未定量对比）。
- **安全性假设**：信任模型依赖内核引擎的不可篡改性，未考虑内核漏洞或CAP_BPF提升攻击。
