## 摘要
LLM智能体越来越多地通过命令行和基于CLI的框架接口解决本地任务，包括代码编辑、仓库检查、数据分析以及文件工作流。现有评估往往强调任务成功率，但部署的本地智能体并非仅由模型构成：CLI介质影响着提示、上下文重放、工具输出、文件访问、终端观测以及停止行为。因此，同一模型在不同CLI下可能产生不同的成功率、Token消耗和成本情况。我们引入了AGENTMETER，一个用于评估CLI中介的本地任务求解智能体中模型-CLI匹配的基准测试，同时提出了AgentMeter分数（AMS），一种基于校准任务努力等级的、以成功为导向且具有成本意识的指标。AgentMeter使用Benchmark90作为完整验证集，Core30作为较低成本的子集，用于在24种完整的模型-CLI配置间进行扩展比较。在Core30上，常见部署标准选择了不同的配置：最高Pass/30选择GLM-5.1与qwen-coder，最低Tok./Pass选择GPT-5.3-Codex与kimi-cli，最低计费美元/Pass选择Qwen3.6+与Codex，而最高AMS选择Qwen3.6+与kimi-cli。Benchmark90验证保留了Top-1配置和Top-3集合，Spearman相关系数为0.765，Kendall相关系数为0.567，AMS平均绝对误差为0.0383。这些结果表明模型选择和CLI选择不应分离，而应将模型-CLI配置作为部署单元进行评估。

## Abstract
LLM agents increasingly solve local tasks through command-line and CLI-based harness interfaces, including code editing, repository inspection, data analysis, and file workflows. Existing evaluations often emphasize task success, but deployed local agents are not models alone: the CLI mediates prompts, context replay, tool outputs, file access, terminal observations, and stopping behavior. As a result, the same model can produce different success, token, and cost profiles under different CLIs. We introduce AGENTMETER, a benchmark for evaluating model-CLI matching in CLI-mediated local task-solving agents, together with AgentMeter Score (AMS), a success-anchored, cost-aware metric over calibrated task-effort tiers. AgentMeter uses Benchmark90 as the full validation set and Core30 as a lower-cost subset for expanded comparison across 24 complete model-CLI configurations. On Core30, common deployment criteria select different configurations: highest Pass/30 selects GLM-5.1 with qwen-coder, lowest Tok./Pass selects GPT-5.3-Codex with kimi-cli, lowest billable USD/Pass selects Qwen3.6+ with Codex, while highest AMS selects Qwen3.6+ with kimi-cli. Benchmark90 validation preserves the Top-1 configuration and Top-3 set, with Spearman correlation 0.765, Kendall correlation 0.567, and AMS MAE 0.0383. These results show that model choice and CLI choice should not be decoupled, and that model-CLI configurations should be evaluated as the deployed unit.

- **整体含义**：提出 AgentMeter 基准和 AgentMeter 分数（AMS），用于评估 CLI 介导的本地任务求解智能体的模型-CLI 匹配度，强调部署时需同时考虑成功率和成本约束。

## 2. 论文提出的方法论

### 核心思想
- 构建一套以成功为导向、成本感知的分层评估框架，通过 **任务难度分层** 和 **预算化质量 + 昂贵失败惩罚** 来量化模型-CLI 配置的匹配效用。

### 关键技术细节

#### 任务集
- **Benchmark90**：90 个任务（Easy/Medium/Hard 各 30 个），来源包括 SkillsBench、Terminal-Bench、DA-Code，覆盖代码、终端、数据、文档等工作流。
- **Core30**：从 Benchmark90 中选取 30 个任务（10/10/10），用于低成本扩展更多配置比较。

#### 任务难度分层公式
- 每个任务 \( i \) 计算努力分数 \( E_i \)：
  \[
  E_i = 0.55(1 - s_i) + 0.25\,q(\ell(\overline{T}_i)) + 0.10\,q(\ell(\overline{U}_i)) + 0.10\,q(\ell(\overline{I}_i))
  \]
  其中 \( s_i = 0.7 p_i + 0.3 r_i \)（通过率 + 平均奖励），\( \overline{T}_i \) 为原始 Token 中位数，\( \overline{U}_i \) 为回合数中位数，\( \overline{I}_i \) 为交互足迹中位数，\( q(\cdot) \) 为百分位数归一化，\( \ell(x) = \log(1+x) \)。分层过程独立于 AMS 和计费成本。

#### 预算化质量（CostAUBQC）
- 对每个难度层 \( g \)，设预算网格 \( B_g \)（见表 1），计算：
  \[
  \text{CBQ}_g(c,b) = \frac{1}{|T_g|} \sum_{i \in T_g} R_i(c) \cdot \mathbf{1}[C_i(c) \le b]
  \]
  \[
  \text{CostAUBQC}_g(c) = \frac{1}{|B_g|} \sum_{b \in B_g} \text{CBQ}_g(c,b)
  \]

#### 昂贵失败率（EFR）
- 对非通过任务，若其计费成本超过层特定阈值 \( \tau_g \) 则记为昂贵失败：
  \[
  \text{EFR}_g(c) = \frac{1}{|T_g|} \sum_{i \in T_g} \mathbf{1}[y_i(c)=0 \land C_i(c) > \tau_g]
  \]

#### AgentMeter 分数（AMS）
- 每层分数：
  \[
  \text{TierScore}_g(c) = \left[ \alpha \cdot \text{SR}_g(c) + (1-\alpha) \cdot \text{CostAUBQC}_g(c) \right] \cdot (1 - \text{EFR}_g(c))
  \]
  其中 \( \alpha=0.6 \)，\( \text{SR}_g \) 为成功锚点（通过率）。
- 最终 AMS 为三层平均：\( \text{AMS}(c) = \frac{1}{3} \sum_{g} \text{TierScore}_g(c) \)。

#### 成本计算
- 按输入/输出/缓存创建/缓存命中 Token 分别计费，美元计价（1 USD = 6.77 CNY，快照 2026-06-04）。

## 3. 实验设计

### 数据集 / 场景
- **Benchmark90**：完整验证集（90 个任务），用于检验排名稳定性。
- **Core30**：低成本子集（30 个任务），用于扩展配置比较（24 种完整模型-CLI 组合）。

### Benchmark 本身
- AgentMeter 即为本文提出的基准，无外部基线对比。但论文对比了不同 **部署标准** 下的选择差异：最高 Pass/30、最低 Tok./Pass、最低 USD/Pass、最高 AMS。

### 对比的方法（配置）
- **6 个模型**：Qwen3.6+, DeepSeek-v4-pro, GLM-5.1, MiniMax-M2.5, Claude Sonnet 4.6, GPT-5.3-Codex。
- **4 个 CLI**：Claude Code, Codex CLI, qwen-coder, kimi-cli。
- 共 24 个完整模型-CLI 配置（6×4）。

### 评价指标
- Pass/30（仅 Core30）、Pass/90（仅 Benchmark90）
- Tok./Pass（每通过任务的 Token 数）
- USD/Pass（每通过任务成本）
- AMS（主要匹配指标）

## 5. 实验数量与充分性

### 实验数量
- **Core30 主实验**：24 个配置 × 30 个任务 = 720 个轨迹（每个配置单次选定尝试）。
- **Benchmark90 验证**：16 个重叠配置（有完整 90 任务数据）× 90 = 1440 个轨迹，共解析 1274 条有效轨迹。
- 未进行多轮重复（单次尝试），未做消融（如 α 变化、不同预算网格）。

### 充分性和公平性
- **优点**：覆盖多个主流模型和 CLI，固定任务环境变化 CLI 隔离 CLI 效应；同时报告 4 种诊断指标，避免单一指标偏差；分层难度基于经验数据而非主观标签。
- **不足**：单次尝试缺乏方差估计；未设计消融实验验证各组件（如 EFR、CostAUBQC）的独立贡献；未对比其他评估方法（如直接成本/成功率比率等）。
- **客观性**：评估过程有明确协议（最新完成选择规则、审计无效轨迹），但部分依赖封闭模型和 API（价格快照、缓存策略），可能随时间变化。

## 6. 论文的主要结论与发现

1. **不同部署标准选择不同配置**：
   - 最高 Pass/30：GLM-5.1 + qwen-coder (18/30)
   - 最低 Tok./Pass：GPT-5.3-Codex + kimi-cli (0.42M tokens/pass)
   - 最低 USD/Pass：Qwen3.6+ + Codex (0.047 USD/Pass)
   - 最高 AMS：Qwen3.6+ + kimi-cli (0.529)

2. **同模型不同 CLI 显著改变 AMS**：例如 Qwen3.6+ 的最佳 CLI（kimi-cli, AMS 0.529）与最差 CLI（Claude Code, AMS 0.178）差距达 0.351。

3. **固定 CLI 也无法得到稳定的模型排序**：例如在 Codex CLI 下，Claude Sonnet 4.6 拥有更高 AMS，但 Qwen3.6+ 成本更低。

4. **Benchmark90 验证排名保持稳定**：Top-1 和 Top-3 配置一致，Spearman 0.765, Kendall 0.567, AMS MAE 0.0383。

5. **失败轨迹比成功更消耗 Token**：中值分别为 381K vs 158K，支持昂贵失败惩罚的必要性。

## 7. 优点

- **方法创新**：首次将 CLI 中介作为评估变量引入，并设计成功-成本权衡指标（AMS）而非仅看成功率或成本。
- **分层设计**：基于任务努力程度区分 Easy/Medium/Hard，使不同难度下的匹配行为可比。
- **多维诊断**：同时报告 Pass、Tok./Pass、USD/Pass、AMS，避免单一指标误导。
- **实验设计**：通过 Core30 低成本扩展 + Benchmark90 验证排名的稳定性，兼顾效率与可信度。
- **开源可复现**：轨迹格式、定价快照、校准参数均公开（论文中给出）。

## 8. 不足与局限

- **实验覆盖**：仅使用了 6 个模型和 4 个 CLI，未覆盖更多开源模型或非 CLI 界面（如 Web/GUI）。
- **单次尝试**：每个配置每任务仅一次选定尝试，未做多轮重复，无法量化随机方差。
- **参数固定**：AMS 中的 α=0.6、预算网格、昂贵阈值 τ_g 均为固定值，未探讨敏感性。
- **价格快照依赖**：成本计算基于接入的 API 定价（2026-06-04），汇率、折扣、缓存策略变动会改变绝对成本。
- **任务集局限**：Benchmark90 难度分层依赖于校准池，可能不适用于其他领域的任务。
- **未评估训练环节**：只关注推理部署效用，不涉及模型训练或 CLI 框架优化。
- **应用限制**：仅适用于 CLI 介导的本地任务，不适用于需要多智能体协作或人类循环的场景。
