## 摘要
LLM代理越来越多地通过命令行和基于CLI的接口解决本地任务，包括代码编辑、仓库检查、数据分析和工作流程。现有评估通常强调任务成功，但部署的本地代理不仅仅是模型：CLI介导了提示、上下文回放、工具输出、文件访问、终端观察和停止行为。因此，相同的模型在不同的CLI下可能产生不同的成功、令牌和成本曲线。我们引入了AGENTMETER，一个用于评估CLI介导的本地任务解决代理中模型-CLI匹配的基准，以及AgentMeter Score (AMS)，一种在校准任务工作量层级上以成功为导向、考虑成本的度量。AgentMeter使用Benchmark90作为完整验证集，Core30作为低成本子集，用于在24个完整的模型-CLI配置之间进行扩展比较。在Core30上，常见的部署标准选择不同的配置：最高Pass/30选择GLM-5.1与qwen-coder，最低Tok./Pass选择GPT-5.3-Codex与kimi-cli，最低计费USD/Pass选择Qwen3.6+与Codex，而最高AMS选择Qwen3.6+与kimi-cli。Benchmark90验证保留了Top-1配置和Top-3集合，Spearman相关系数为0.765，Kendall相关系数为0.567，AMS MAE为0.0383。这些结果表明，模型选择和CLI选择不应解耦，并且模型-CLI配置应作为部署单元进行评估。

## Abstract
LLM agents increasingly solve local tasks through command-line and CLI-based harness interfaces, including code editing, repository inspection, data analysis, and file workflows. Existing evaluations often emphasize task success, but deployed local agents are not models alone: the CLI mediates prompts, context replay, tool outputs, file access, terminal observations, and stopping behavior. As a result, the same model can produce different success, token, and cost profiles under different CLIs. We introduce AGENTMETER, a benchmark for evaluating model-CLI matching in CLI-mediated local task-solving agents, together with AgentMeter Score (AMS), a success-anchored, cost-aware metric over calibrated task-effort tiers. AgentMeter uses Benchmark90 as the full validation set and Core30 as a lower-cost subset for expanded comparison across 24 complete model-CLI configurations. On Core30, common deployment criteria select different configurations: highest Pass/30 selects GLM-5.1 with qwen-coder, lowest Tok./Pass selects GPT-5.3-Codex with kimi-cli, lowest billable USD/Pass selects Qwen3.6+ with Codex, while highest AMS selects Qwen3.6+ with kimi-cli. Benchmark90 validation preserves the Top-1 configuration and Top-3 set, with Spearman correlation 0.765, Kendall correlation 0.567, and AMS MAE 0.0383. These results show that model choice and CLI choice should not be decoupled, and that model-CLI configurations should be evaluated as the deployed unit.

### 论文核心问题与整体含义（研究动机和背景）
- **研究动机**：现有LLM Agent评估通常只关注任务是否成功（如通过率），却忽略了命令行界面（CLI）对代理行为的显著影响。CLI不仅作为传输层，还中介了提示布局、上下文回放、工具输出格式、文件访问、终端观察和停止行为，这些都会影响模型获得的证据和轨迹终点。因此，同一模型在不同CLI下可能表现出不同的成功率、token消耗和计费成本。
- **核心问题**：模型和CLI的配对（model–CLI configuration）应该作为部署的基本单元进行评估，而非将两者解耦单独考量。当前缺乏一个以成功锚定且成本感知的基准来量化这种匹配质量。
- **整体含义**：部署本地任务求解Agent时，必须联合考虑模型和CLI的选择，才能获得真实的性能、效率和成本权衡。

### 方法论：核心思想、关键技术细节
- **核心思想**：提出AgentMeter基准，包含两个数据集（Benchmark90和Core30）和一个综合度量AgentMeter Score (AMS)。AMS是成功锚定（success-anchored）、成本感知（cost-aware）且按任务难度分层校准（tier-calibrated）的匹配度量。
- **关键技术细节**：
  - **任务难度分层**：通过经验公式计算每个任务的努力分数 $E_i$，综合通过率、平均奖励、中位token量、中位回合数等，将Benchmark90的90个任务分为Easy、Medium、Hard三个层级（各30个）。层级划分独立于AMS计算，避免循环依赖。
  - **Token经济度量**：定义原始token消耗 $T_i$、计费成本 $C_i$（按缓存感知定价公式 $C_i = p_{in} N_i + p_{out} Y_i + p_{create} A_i + p_{hit} H_i$），以及三个传统诊断指标：Pass count（通过数）、Tok./Pass（每次通过的token量）、USD/Pass（每次通过的计费成本）。
  - **AMS计算**：对每个层级 $g$：
    - 成功锚定率 $SR_g(c) = \frac{1}{|T_g|} \sum_i R_i(c)$。
    - 成本预算质量 $CostAUBQC_g(c)$：在预定义的预算网格 $B_g$ 上，对每个预算 $b$ 计算满足预算的任务质量占比，再求平均。
    - 昂贵失败率 $EFR_g(c)$：对非通过且成本超过阈值 $\tau_g$ 的任务计数。
    - 层级得分：$TierScore_g(c) = [\alpha SR_g(c) + (1-\alpha) CostAUBQC_g(c)] \cdot (1 - EFR_g(c))$，其中 $\alpha=0.6$。
    - 最终AMS为三个层级得分的均值：$AMS(c) = \frac13 \sum_g TierScore_g(c)$。
  - **算法流程**：先对每个模型-CLI-任务组合运行一次，记录pass/quality、token分解、成本等；再按任务层级计算各项组件，最终得到AMS。

### 主要结论与发现
1. **不同部署标准选择不同配置**：在Core30上，最高Pass/30（18/30）是GLM-5.1 + qwen-coder；最低Tok./Pass（0.42M/pass）是GPT-5.3-Codex + kimi-cli；最低USD/Pass（0.047/pass）是Qwen3.6+ + Codex；最高AMS（0.529）是Qwen3.6+ + kimi-cli。说明仅凭单一指标无法反映整体部署效用。
2. **同一模型在不同CLI下AMS差异显著**：例如Qwen3.6+使用kimi-cli AMS为0.529，使用Claude Code仅0.178，差异达0.351。验证了CLI不是中性传输层。
3. **模型-CLI应联合评估**：固定模型或固定CLI都无法获得稳定的模型排名，最佳配对需要基于实际部署场景。
4. **Benchmark90验证保持排序一致性**：Core30上的Top-1和Top-3配置在Benchmark90上保持一致；Spearman 0.765，Kendall 0.567，AMS MAE 0.0383，说明Core30作为低成本子集能有效反映全量集结果。
5. **失败轨迹比成功轨迹更昂贵**：中位失败token 381K vs 中位成功158K，支持了AMS中包含昂贵失败惩罚的合理性。

### 优点
- **问题定义新颖**：首次正式提出“模型-CLI匹配”评估问题，指出部署单元应是模型-CLI配对而非单边。
- **度量设计合理**：AMS同时考虑成功、预算内质量、昂贵失败，且按任务难度分层，避免了单一指标（如通过率或最低成本）的缺陷。通过α参数可调节成功与成本的权重。
- **实验设计严谨**：任务难度分层基于多因素经验公式，且与最终AMS计算分离，避免数据泄露；采用确定性选择规则，可复现；审计排除基础设施问题。
- **覆盖全面**：6个模型、4个CLI、90个任务，涵盖多种本地工作流，提供丰富对比数据。

### 不足与局限
- **实验局限**：
