## 摘要
AI代理的采用正在迅速增加。终端AI代理，即在终端环境中运行的AI代理，是一种广泛使用的AI代理类型。终端AI代理严重依赖shell命令执行来与主机系统交互。它们采用三列表命令门控机制来减轻命令执行带来的安全风险，其中黑名单作为承载组件。然而，现代操作系统通常附带大量且不断扩展的shell命令，这些命令具有复杂的功能。我们的观察是，即使是Claude Code的内置黑名单（由开发者精心维护）也可能忽略绕过命令，使其失效。这种疏忽导致脆弱的命令黑名单甚至无法阻止从业者期望阻止的操作。本文首次系统性地描述了终端AI代理中命令黑名单的脆弱性。本文形式化了命令黑名单脆弱性问题，并提出了一种LLM驱动的流水线CmdNeedle来检测这种脆弱性。它提示LLM提出可能的绕过方式，并使用来自验证器（在沙箱中执行这些绕过方式）的反馈迭代修复它们。在评估中，我们将CmdNeedle应用于从GitHub收集的1,709个真实世界命令黑名单（包含13,332条黑名单规则）。评估显示了几项关键发现，包括69.0–98.6%的黑名单是脆弱的，这种脆弱性在项目和代理之间一致出现，以及这种脆弱性的几个可能根本原因的有效性。我们的流水线和发现有望促进未来关于AI代理使用的命令黑名单的研究和实践。

## Abstract
The adoption of AI agents is increasing rapidly. Terminal AI agents, i.e., AI agents that run in terminal environments, are a widely used type of AI agents. Terminal AI agents rely heavily on shell command execution to interact with the host systems. They adopt a three-list command-gating mechanism to mitigate security risks introduced by command execution, with denylists serving as the load-bearing component. However, modern operating systems often ship a large, ever-expanding set of shell commands with complex functionalities. Our observation is that even a built-in denylist of Claude Code, well-maintained by its developers, can overlook bypass commands that invalidate its effectiveness. Such negligence leads to fragile command denylists that cannot even block operations that practitioners expect them to block.   This paper presents the first systematic characterization of command denylist fragility in terminal AI agents. The paper formalizes the command denylist fragility problem and proposes an LLM-driven pipeline, CmdNeedle, to detect such fragility. It prompts the LLM to propose possible bypasses and iteratively repairs them using feedback from a validator that executes them in a sandbox. In the evaluation, we applied CmdNeedle to 1,709 real-world command denylists (containing 13,332 denylist rules) collected from GitHub. The evaluation shows several key findings, including that 69.0--98.6% of the denylists are fragile, that this fragility occurs consistently across projects and agents, and the validity of several possible root causes for this fragility. Our pipeline and findings will hopefully facilitate future research and practice regarding the command denylists used by AI agents.

## 1. 论文的核心问题与整体含义（研究动机和背景）
- **核心问题**：终端AI代理（如Claude Code、Codex、OpenCode）依赖命令黑名单来阻止危险操作，但黑名单往往不完备——即使经过精心维护的内置黑名单也会遗漏可执行同样操作的绕过命令（如`awk`绕过Claude Code的代码执行黑名单）。这种脆弱性使黑名单无法有效阻止攻击者预期的操作，而由于“批准疲劳”用户会默认同意93%的请求，黑名单成为三列表门控机制中最关键的防线。
- **整体含义**：首次系统性地定义并度量命令黑名单的“不完整阻塞”问题，揭示其严重性和普遍性，为后续安全加固提供实证基础和检测工具。

## 2. 论文提出的方法论：核心思想、关键技术细节
- **形式化定义**：
  - 定义黑名单规则为谓词，命令若被规则匹配则被拒绝。
  - 定义“阻塞操作”为命令执行后对文件系统留下的可观测副作用（共七种：读、写、创建、删除、复制、改权限、改属主）。
  - 定义“不完整阻塞”：黑名单阻塞某操作，但存在至少一个未列入黑名单的命令也能执行该操作（即绕过命令）。
- **CmdNeedle流水线**（三步循环）：
  1. **候选枚举**：用LLM（Claude Sonnet 4.6）基于命令文档（man页、--help、GTFOBins）提出候选操作和参数，支持占位符（如`$P`表示任意路径）。
  2. **执行验证**：在沙箱（Bubblewrap + OverlayFS）中实际执行命令，用预定义的oracle检查副作用（如读操作验证传入的canary是否出现在stdout/stderr）。
  3. **迭代修复**：验证失败的候选返回LLM，附带错误信息，LLM重新生成修正版，最多循环5轮。最终将已验证的操作与黑名单阻塞的操作取交集，得到绕过集合。
- **核心思想**：利用LLM的shell命令生成能力提出潜在绕过，再通过沙盒执行严格验证，确保结果可靠（无假阳性）。

## 3. 实验设计：数据集 / 场景、benchmark、对比方法
- **数据集**：从GitHub收集了1,709个真实AI代理命令黑名单（共13,332条规则），来自三类代理：Claude Code（1,000个）、Codex（136个）、OpenCode（573个）。项目星标分布从0到≥1000。
- **场景**：以标准Debian 13.5 Docker镜像为参考主机，遍历所有可执行路径构成命令宇宙。
- **Benchmark / 对比方法**：本文是首项系统性研究，未对比其他自动化检测方法。实验聚焦于自评估：对每个黑名单/操作计算不完整阻塞率、按星标和代理分层、验证根因假设、统计修复负担。
- **评估指标**：不完整阻塞率（RQ1）、分层不完整阻塞率（RQ2）、命令流行度与绕过概率的逻辑回归（RQ3-H1）、多用途命令与单用途命令的Mann-Whitney U检验（RQ3-H2）、TLDR文档中是否提及操作与绕过率的对比（RQ3-H3）、最小/平均/最大绕过命令数量（RQ4）。

## 6. 论文的主要结论与发现
1. **问题严重**：69.0–98.6%的黑名单对至少一种操作存在不完整阻塞（即存在绕过命令）。
2. **普遍性**：脆弱性在高星标项目和低星标项目中均高发（>44.4%）；在所有三个代理中均高发（>46.2%）。
3. **根因验证**：
   - H1（忽视）：命令越不流行（流行度排名越高），成为绕过的概率显著升高（逻辑回归斜率显著）。
   - H2（多功能性）：能执行多种操作的命令绕过更多黑名单（中位数664 vs 281，p=0.006，Cliff’s δ=0.30）。
   - H3（语义鸿沟）：被反驳——实际绕过命令的TLDR文档中大多已提及该操作，说明能力是公开的而非隐藏。
4. **修复负担重**：彻底阻塞一个操作平均需要添加217个额外命令（如读操作），最高可达603个。

## 7. 优点
- **首次系统化形式化**：将黑名单脆弱性精确定义为“不完整阻塞”，并给出可计算的操作集合。
- **LLM+沙箱组合**：利用LLM的高质量生成能力枚举候选，再通过执行验证消除幻觉，兼顾覆盖率和准确性。
- **大规模真实数据集**：收集1709个真实黑名单，覆盖主流代理，结果具有现实参考价值。
- **根因分析有统计支持**：三个假设均用数据检验，结论可信，且反驳了“语义鸿沟”这一直观猜测。
- **可复现性**：承诺开源代码和数据，便于社区复现和扩展。

## 8. 不足与局限
- **LLM枚举不完备**：只能发现LLM“想到”的绕过命令，因此报告的脆弱性只是下界；实际可能更严重。

- **无对比基线**：未与传统文档挖掘、静态分析等方法对比，难以评估LLM方法的相对优势和成本效益。
- **修复方案评估不完整**：仅统计了需添加的命令数量，未讨论实际修复策略（如正则扩展而非枚举）。
