## 摘要
在智能体网络时代，基于LLM的智能体越来越多地将网络服务作为工具调用，但大多数接口仍然是\emph{静态端点}，难以表达包含循环、条件、连接和重试的长周期工作流。我们提出ToolPro，它将智能体的工具意图表示为\emph{可执行的工具程序}，紧凑地编码多步服务交互并带有显式的效果类型。ToolPro结合了约束引导的程序构建、用于精确一次状态修改调用的效果感知重放，以及一个配置文件驱动的策略，用于决定程序执行何时优于逐步调用。我们在MCP风格的服务上实例化ToolPro，并采用WebAssembly沙箱，在真实应用的各种工作流上进行评估。ToolPro将端到端延迟降低最多53.4%，客户端流量减少最多96.1%，在网络延迟较高和工作流复杂度较高时收益更大。

## Abstract
In the agentic web era, LLM-based agents increasingly invoke web services as tools, yet most interfaces remain \emph{static endpoints} that poorly express long-horizon workflows with loops, conditionals, joins, and retries. We present ToolPro, which represents an agent's tool intent as an \emph{executable tool program} that compactly encodes multi-step service interactions with explicit effect types. ToolPro combines constraint-guided program construction, effect-aware replay for exactly-once state-modifying calls, and a profile-driven policy that decides when program execution outperforms stepwise calling. We instantiate ToolPro over MCP-style services with WebAssembly sandboxing and evaluate it on diverse workflows of real-world applications. ToolPro reduces end-to-end latency by up to 53.4\% and client-side traffic by up to 96.1\%, with larger gains under higher network latency and workflow complexity.

## 1. 论文的核心问题与整体含义

**研究动机与背景**：当前基于LLM的智能体越来越多地通过调用Web服务（工具）来完成复杂任务，但大部分Web服务的接口仍然是**静态端点**（static endpoints）。这种接口设计仅适用于单次查询，无法高效表达需要循环、条件分支、中间数据绑定、重试等控制流的多步工作流。智能体只能通过“逐步调用+多轮推理”的外部化方式实现控制流，导致：

- 大量网络往返（RTT）和客户端推理轮次；
- 数据过度获取或获取不足；
- 部分失败时级联重试，容易重复副作用、破坏服务状态。

**整体意义**：论文提出**工具程序（Tool Program）** 作为智能体面向服务的新接口。将多步交互意图封装为一个可执行程序，提交给服务端运行，从而将控制流从客户端移到服务端，实现回合减少、副作用可控、可修复。这一思路为构建更高效、灵活的智能体Web服务奠定了重要基础。

## 2. 方法论：核心思想与关键技术

**核心思想**：将工具意图显式表示为**可执行工具程序**，该程序使用受限编程语言表达，并显式标注每个调用点的效果类型（READ / WRITE）。客户端只需提交一个程序对象，服务端运行时负责编译、修复、执行，并保证语义一致性和重试安全性。

**关键技术细节**：

1. **约束引导的程序构建**：
   - **客户端合成**：给定任务意图和工具规范，LLM生成候选程序，进行轻量接口检查（端点覆盖、控制流骨架、值流合理性）。
   - **服务端投影**：将程序投影到受约束的接口程序表面（仅允许结构化控制流、统一CALL调用、禁止异常/线程/动态链接等）。
   - **编译与修复**：使用编译器诊断和运行时跟踪进行有限次数的原位修复（in-place repair）；若修复失败则回退到逐步调用。

2. **效果感知重放**：
   - 对每个WRITE端点维护历史日志H和当前日志W；跨修复重执行时，已完成WRITE的结果从H中重放，避免重复副作用。
   - 要求重放前修复后的程序不能改变已提交WRITE的参数或顺序，否则回退逐步调用。
   - 算法流程：每次重执行前将W追加到H，清空W并重置`used`标志；执行时READ始终转发，WRITE首先尝试匹配H中未使用的条目（相同e,a），匹配则返回缓存结果，否则执行并记录到W。

3. **配置文件驱动的合并策略**：
   - 维护近期运行的移动平均：TRTT（网络往返时间）、TDEC（每步决策开销）、TBUILD（程序构建开销）。
   - 根据候选程序预计调用次数N，按公式 `ΔT = (N−1)·(TRTT+TDEC) − TBUILD` 判断：若ΔT>0则选程序模式，否则选逐步调用。
   - 冷启动时先用少量逐步运行初始化配置，待稳定后应用决策规则。
