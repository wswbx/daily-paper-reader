## 摘要
从事研究（提出想法、编写和运行代码、分析结果）的LLM智能体已经可以从研究问题到图表完成一项研究，但仍不能完全信任。连续两次提问同一个问题会返回不同的答案；智能体声称一个从未执行产生的数字，而工具的使用并不能阻止这一点，因为智能体报告的内容与其工具返回的结果之间没有任何绑定；上游的一小点更改会静默地使下游结果过时，且无法列出哪些过时了；智能体会重复运行预处理并重写它已经产生的代码。我们认为这些失败有一个共同的根源：现今智能体循环的每一步都是一个随机的LLM调用，其内部状态无人（包括智能体本身）可以检查。我们不是试图窥探LLM内部，而是从数据库中汲取经验：数据库无需被监视即可获得信任，因为定义良好的状态上的确定性操作符通过构造保证了它们的承诺。我们提议以同样的方式组织一个研究项目。该项目存在于一个确定性的、版本化的数据流引擎（实际上，是一个基于物化视图的查询计划）中，而LLM与用户一起是一个随机的编译器，只能编辑该计划。执行器从不调用LLM；LLM的输出仅作为版本化的代码和数据进入，然后由执行器运行，任何断言的结果只有在其背后有执行记录时才能进入记录。在这个边界上的五条设计规则将熟悉的数据库机制（从版本控制和数据起源到增量维护和基于成本的调度）转化为保证，使研究变得可靠、无浪费、透明和协作。本报告介绍了诊断、需求和设计；保证的演练、原型和研究议程将在完整版本中呈现，正在准备中。我们认为，LLM应该是查询编译器，而不是执行器。

## Abstract
LLM agents that conduct research (proposing ideas, writing and running code, analyzing results) can already carry a study from research question to figures, yet cannot be fully trusted. The same question asked twice in a row returns different answers; the agent announces a number that no execution produced, and tool use does not prevent this, because nothing binds what the agent reports to what its tools returned; a small upstream change leaves downstream results silently stale, with no way to list which ones; and the agent re-runs preprocessing and rewrites code it has already produced. We argue these failures share one root: every step of today's agent loop is a stochastic LLM call whose internal state nobody, including the agent, can check. Rather than trying to see inside the LLM, we take a lesson from databases, which earn trust without being watched, because deterministic operators over well-defined state make their guarantees hold by construction. We propose organizing a research project the same way. The project lives in a deterministic, versioned dataflow engine (in effect, a query plan over materialized views), and the LLM, together with the user, is a stochastic compiler that may only edit that plan. The executor never calls the LLM; LLM output enters only as versioned code and data that the executor then runs, and any asserted result enters the record only with an execution behind it. Five design rules at this boundary turn familiar database machinery, from versioning and provenance to incremental maintenance and cost-based scheduling, into guarantees that make research reliable, non-wasteful, transparent, and collaborative. This report presents the diagnosis, the requirements, and the design; the guarantee walkthrough, a prototype, and the research agenda appear in the full version, in preparation. The LLM, we argue, should be the query compiler, never the executor.

## 1. 论文的核心问题与整体含义（研究动机和背景）

- **痛点：当前 LLM 驱动的科研智能体（ADRS）存在四大缺陷**：
  - **不可靠**：相同问题重复问返回不同结果；智能体报告的数字可能从未执行过；工具使用不能保证一致性；上游小改动静默导致下游结果过时；没有版本控制无法回滚。
  - **浪费资源**：重复运行预处理、重写已写过的代码、重复发送相同文件内容；研究显示智能体生成的子计划中只有 10–20% 是唯一的，其余都是近似重复。
  - **不透明**：研究者只能通过重写提示词来引导智能体，无法直接查看计划状态。
  - **不协作**：项目状态仅存在于聊天记录中，新加入者需要人类重新解释，评审只能依赖 PDF。

- **根因**：当前智能体的每个步骤都是对 LLM 的随机调用，其内部状态对外部（包括智能体自身）不可检查。输出文本不可靠，且没有机制强制验证。

- **核心洞察**：借鉴数据库系统的确定性执行和信任机制——DBMS 通过确定性操作符和定义良好的状态保证正确性，无需监视。论文提出将整个研究项目组织为一个确定性、版本化的数据流引擎（类似查询计划），LLM 和用户共同作为随机的**编译器**（只编辑计划），而执行器永远不调用 LLM。

## 2. 论文提出的方法论：核心思想、关键技术细节

- **两层模型**：
  - **L1（确定性子层）**：项目的记录和执行引擎。包含：
    - 不可变工件（Artifact，S1），由（key, version）标识，版本包含内容哈希和输入版本（S2）。
    - 操作符（Operator，S3），声明读取的键和写入的键，运行时来自固定确定性集合（S4）。
    - 仅追加的注册表（Registry R，S5）和执行日志（ExecLog E，S6）。
    - 缓存 K（S7）：签名（运行时+输入版本哈希）到工件的映射，相同签名重用结果。
    - 运行函数（run, S8）是纯函数，从不调用 LLM。
    - 依赖性传播（S9）：写操作仅将受影响的读者标记为“过时”，粒度到字段级（增量视图维护）。
  - **L2（随机编译器）**：包含 LLM 和用户：
    - 接收请求（Request, S10），生成视图（View, S11）：只读投影，从依赖闭包中组装上下文（图5d）。
    - 编辑函数（edit, S12）：**系统中唯一的随机步骤**，输出 DagEdit（S13），可添加/重连节点、放置工件、冻结子树等。
    - 编辑缓存（EditCache, S14）：通过规范化请求和视图摘要哈希，相同请求+相同视图重放之前编辑，避免重复调用 LLM。
    - 工作状态（State, S15）：包括目标、成功谓词、注释、预算。
    - 观察函数（observe, S16）：仅从执行结果更新状态。

- **五条设计规则（D1–D5）**：
  1. **D1（确定性）**：L1 运行时是确定性函数；重新物化图产生相同字节。
  2. **D2（仅追加）**：记录永不覆盖。
  3. **D3（约束）**：edit 是唯一的随机关系。
  4. **D4（幂等性）**：缓存查询是签名的函数；相同请求+相同视图产生相同编辑和相同结果。
  5. **D5（证据门）**：记录只接受来自 run 的追加；编译器没有写入路径。LLM 的断言只能成为注释或添加 Eval 节点，节点执行输出才能进入记录。

- **上下文管理**：基于依赖闭包而非对话历史。每个请求的视图是确定性的，大小与相关结构相关，不会遗忘（图5对比了四种方法）。使用摘要（Digest）压缩非主干祖先。

- **核心结论**：**LLM 应该是查询编译器，而不是执行器**。将非确定性约束在编译器内，通过 D1–D5 规则，可以像数据库一样“由构造保证”可靠性、无浪费、透明和协作。
